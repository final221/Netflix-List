## D01 — represent each initialization operation once

**Best first bounded reduction; scheduler portion demonstrated.**

`src/app/my-list-session.js` holds a scheduled run in four values: `scheduled`, `scheduledSessionToken`, `scheduledRunTimer`, `scheduledRunDueAt`. They are set/reset together in scheduling and route retirement. The callback separately compares timer identity; due time supplies earliest-run coalescing. One nullable record `{ sessionToken, dueAt, timer }` can own both facts and callback identity. Clearing an obsolete callback must not clear a newer record.

A temporary prototype made that replacement in place, preserving the one-millisecond due-time tolerance, delay normalization, blocked-route admission, timer cancellation and route recheck. Build/check and **all 532 unchanged tests passed**, zero failures/cancellations/skips. Session source fell from **2,924 lines / 154,554 bytes** to **2,906 / 153,952**; bundle fell to **19,261 lines / 887,143 bytes**. Net: **18 authored lines / 602 bytes**, **469 generated bytes**. Source and artifact were restored byte-for-byte in a finally block. No prototype is shipped, and this result does not prove exhaustive timer interleavings.

Running initialization is similarly represented by `running`, `runningSessionToken`, and `initializationDeferral`. `beginRunningSession` already creates an exact owner object; `clearRunningSession` compares both owner and token before releasing reconciliation. The stronger destination is one current initialization operation, with its token and ticket, and derived running diagnostics. However, `resetDetachedTargetState` currently clears the deferral without clearing the running fields. That transition must be modeled explicitly; deleting the booleans and deriving everything from the ticket immediately would change behavior. Ticket disposal and operation completion are different events.

Blocked state also has two forms: a generic initialization failure can set `initializationBlockedSessionToken` without `nativeInitializationFailure`; only selected native readiness failures save section/scroller/track for the single replacement-source recovery. One blocked record with optional native recovery facts can represent this distinction. Deriving every blocked state from the native failure would incorrectly allow ordinary failures to restart.

**Do not collapse all state into one exclusive enum.** Scheduled work can coexist with a running initialization, and mismatch reinitialization has a separate dialog/admission lifetime. Route scope, initialization owner, scheduled owner and blocked cause are related but independent. Keep them independent and make each internally authoritative. Keep source cleanup policies distinct: detach, route retirement, mismatch and native replacement differ in whether queued membership resumes and whether accepted viewing/material survive.

Acceptance beyond the prototype: preserve snapshot diagnostic fields; strengthen the composed scheduler scenario to prove an earlier DOM event pulls a 1,200 ms fallback forward, a later request does not postpone it, and manually delivered old timer work cannot clear a replacement schedule. Existing initialization-click deferral, responsive deferral, route reentry, mismatch retirement and one-attempt recovery cases remain. No generic task framework or new abstraction layer is necessary.

## D02 — simplify validation plumbing while retaining separate proofs

**Limited common mechanics; not a large deletion candidate on current evidence.**

`src/netflix/carousel/carousel.js` holds five private receipt registries. They look alike at allocation, but carry different proofs:

| Receipt | Unique validity or authority |
| --- | --- |
| Binding | Issued handle identity, route/generation, accepted references and connectedness |
| Source card | Binding plus model revision, live slot/href/React index, filled membership and indicator-page ownership |
| Mapping result | Guarded mapping operation plus result revision, including committed replacement model |
| Preparation | Exclusive preparation owner, model/generation, readiness and one-time complete-count acceptance |
| Observation | Operation admission plus fact-specific live validation, with synchronous read-scope caching |

`assertMapping`, `assertPreparation` and `assertObservation` each refresh native interpretation between guard calls. Observation additionally runs a fact validator inside a native read scope; preparation deliberately changes its admitted mapping generation when complete count is accepted. A universal generation check would miss these distinctions. Binding/source receipts are capabilities, not redundant copies of ordinary records.

A shared receipt issuer/checker could encode repeated lookup/reject plumbing, but it still needs owner-specific validation and stage-specific errors. Preparation also needs direct private access to its one-time acceptance owner. Sharing a WeakMap or moving all checks to a helper does not remove these rules and is unlikely to produce a substantial net saving. Keep public intent operations and private model ownership. Do not add a callback registry just to eliminate three short wrappers.

The more useful interface opportunity is **one admitted card-resolution attempt across expected-page, preferred refresh and bounded search**. The session currently assembles common inputs and checks route/source/hover ownership in `resolveExpectedPageSourceItem` (1700), `refreshStaleSourceOnPreferredPage` (1761), `locateActiveSourceItem` (1774), and `prepareMountedPage` (1829–2151). This 453-line region is a review surface, not 453 removable lines. Carousel already exposes `resolveCard` modes, while the session reconstructs the attempt around each call and later repairs page hints/card attributes.

A session-local attempt can capture parent, native binding, exact membership/card and hover intent once, provide one admission operation, and make each stage return the same resolution shape. Repeated setup/getter adapters and cancellation handling can then disappear rather than merely move into another file. Keep expected-page proof, mismatch thresholds, preferred hydration, search radius/order, mapping repair and prompt suppression explicit. Session still owns list/grid policy; carousel still owns native movement. A new carousel operation that reaches into list/grid membership would violate the existing boundary.

Relevant protections are already observable: off-page native hover preserves accepted order; physical intent is rechecked after responsive stability; hidden/control cards cannot prepare; mismatch acceptance/cancellation/reentry are separate; source handles reject recycled slots and replaced models; queued recovery cannot click after mapping/route replacement. Before changing the attempt contract, add only missing composed cases for cancellation or source replacement **between expected-page failure and preferred/search recovery**, and for distinguishing bounded ordinary search from mutation recovery. Preserve native read counts, retry/radius limits and reason/stage diagnostics. This is the highest-value broader design candidate, but has no prototype or defensible net-size estimate yet.

## D03 — eliminate avoidable collection intermediates

**Real redundant representation on the preferred wire path; boundary change required.**

R03 already made the public list transfer the sole capture interpreter/releaser. Remaining preferred collection still performs:

```text
list-data scalar records
  -> buildItems: enriched mutable objects with page/logicalIndex/cardTemplate/graphql
  -> prepareRecords: frozen scalar records + material/page maps + captured-input ledger
  -> staged membership + native page hints
  -> grid registry and exact card handles
```

`src/list/collection.js:121–166` builds one wrapper per accepted wire record, attaches the same template and page facts, then `prepareRecords:167–198` converts those wrappers again. `src/app/my-list-session.js:2153–2203` stages the resulting transfer, membership and hints before grid acceptance. The wire path can instead construct canonical records and a staged material/page transfer directly during cooperative construction. This removes an intermediate item form and its second normalization pass; it is a genuine conceptual reduction if the callers actually stop accepting that intermediate form.

Do **not** combine membership, page hints and grid cards into one mutable object. Membership/order are authoritative list facts; page hints can change without changing order; rendered handles retire when a card is replaced; retained Undo material has exact correlation/expiry. Their different lifetimes require separate authority. Similarly, the current input ledger snapshots material identity so accepted release cannot clear a newer capture. A straight `delete input.snapshot` or one shared record map would weaken the contract.

The direct preferred transfer should keep completeness/duplicate proof before publication, canonical identity, template reuse, page hints, and the 24-item/6 ms cooperative quantum. Rejection/cancellation must discard staging without consuming someone else's material; accepted publication must release exact captures. Mounted/native collection and native Add still need capture-to-record adaptation at their input boundary. Use one transfer builder with separate producers, rather than a second preferred-transfer implementation alongside the existing path.

Affected contracts include `collectLogical`, `preparePreferred`, `collectForPublication` and their focused tests. Returning a transfer earlier also changes the app's count/status and fallback admission, so this is more than deleting `buildItems`. Preserve the complete-wire-order session case, mounted reuse with no request, incomplete mounted fallback, failed fresh request native traversal, construction cancellation, transfer discard/release host failure, reentrant publication, native Add and retained/native Undo. Add a composed assertion that a rejected preferred stage neither consumes material nor publishes partial membership before native fallback. No line or allocation-performance saving is claimed without a measured implementation.

## Ordered decision

1. Implement D01's scheduled owner first, then the running/blocked records as separately verified transitions. The scheduler prototype is ready evidence, not the final release or full lifecycle redesign.
2. Establish the admitted hover-resolution attempt from D02. Require less duplicated coordination and a smaller combined source total; extracting 453 lines to a new file alone is not success.
3. Make D03's canonical staged transfer the collection result, adapting native inputs at the boundary. Require removal of the enriched preferred item representation and its conversion path, not a parallel implementation.
4. Reconsider shared carousel receipt plumbing only if those changes expose a substantial common rule. Current evidence favors keeping its distinct validators.

These changes preserve the implemented feature owners and are not a new whole-codebase migration. If implementation needs different ownership/layout, update Migration.md's target contracts explicitly before applying that step. Re-review guards and actual caller contracts at each step; passing tests alone does not make an untested native compatibility branch unnecessary.

The review finds plausible structural excess, especially repeated session coordination and preferred collection wrapping. It does **not** establish that the whole 19,276-line artifact is essential, or that a much smaller implementation can preserve every capability. The only newly measured saving is the restored scheduler prototype. Documentation is the only retained change in this run; main stays on release 1.4.60 for the user's live Netflix check.
